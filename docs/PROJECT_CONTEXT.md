## Цель проекта

Клиент диетолога: подбор продуктов и контроль нутриентов относительно суточных норм.

Сейчас это **Angular 15** SPA. Рассматривается упрощённый вариант **в одном HTML** с формой (по духу UN_Calculator) и хранением данных в **IndexedDB**, без раздувания и без полного скана большой матрицы на каждое действие.

Связанный бэкенд: Spring Boot + PostgreSQL (`jdbc:postgresql://localhost:5432/dietolog`).

## Схема данных (общая для сервера и клиента)

Три сущности (имена как в Postgres / JPA):

| Таблица | Записей (снимок в клиенте) | Поля (ключевые) |
|---------|----------------------------|-----------------|
| `nutrients` | **43** | `_id`, `name`, `units`, `min_dailyrate`, `max_dailyrate`, `koeff_to_miligr`, `info`, `hint`, `val`, `excluded` |
| `products` | **~1231** | `_id`, `name`, `lowercase`, `val`, `hint`, `rownumber`, `isrecommended`, `isnotrecommended`, `excluded`, `fastdegree` |
| `info` | **~26322** | `_id`, `product`, `nutrient`, `value` (на 100 г), `perc1on100gr` |

Связь: `info.product` → `products._id`, `info.nutrient` → `nutrients._id`.

### Где лежат данные в клиенте

- Основной режим: `localData = true` в `ProductsAndNutrientsComponent` — данные из `src/app/model/static.datasource.ts` (~3.3 МБ; дубликат массивов в `static.datasource.arrays.ts`).
- Опционально: HTTP к `http://localhost:8080/api/...` (`DataService`) — тот же логический набор, что в Postgres.
- Состояние раскладки (выбранные `val`, excluded, params) — `localStorage` (`rz_dietolog_configuration_*`).

Источник справочных ссылок `nutrients.info`: **edaplus.info**. В `static.datasource.ts` есть SQL-комментарии экспорта из Postgres в JS-объекты.

### Покрытие нутриентов (факт на 2026-07-29)

- Макросы / Ca / K / Fe и т.п. — почти у всех продуктов (~90–99%).
- **Йод (I), `_id=29`:** есть в справочнике нутриентов, но значения только у **~128 / 1231 (~10%)** продуктов.
- Аналогично разрежены: ванадий (~2%), кремний, бор, витамин D/H, хром, фтор, кобальт, молибден и др. (&lt;20% продуктов).

Вывод: «по йоду почти ни у кого нет данных» — верно как про **матрицу `info`**, не как про отсутствие нутриента в списке.

### Оценки размера для IndexedDB (компактный пакет)

| Формат | Сырой ≈ | zlib ≈ |
|--------|---------|--------|
| Полные объекты `info` как в TS | 1.9 МБ | 180 КБ |
| Тройки `[product, nutrient, value]` | 430 КБ | 110 КБ |
| Параллельные массивы | 380 КБ | 60 КБ |

IndexedDB по лимитам вмещает текущий объём с запасом. Риск тормозов — не «положили в IDB», а полный скан 26k строк без индексов / без рабочего среза в памяти.

## Ключевые решения (анализ, ещё не реализовано)

1. **Не заменять** всю русскую базу на USDA целиком (ломаются имена/`_id`, раздувание).
2. **Дополнять** sparse-нутриенты (йод и соседние) точечно из более плотных источников (USDA Iodine DB / FoodData Central) с маппингом на свои `_id`.
3. Целевое хранение упрощённого клиента: **IndexedDB** — компактные справочники + матрица; индексы под `(productId, nutrientId)` / по `nutrientId`; в память — только выбранные продукты и нужные нутриенты.
4. `perc1on100gr` можно не хранить — считать от `min_dailyrate` (как `recalcPerc1on100gr()`).
5. Упрощённый UI — один HTML + форма; действия формы — по отдельным указаниям Sergey.
